# Internationalization (i18n)

[next-intl](https://next-intl.dev) 4, three languages: English (`en`, default), Portuguese (`pt`) and Spanish (`es`).

## Language policy

- **The interface is translated** (en default, pt, es) through next-intl.
- **User content is never translated.**
- **Code, comments, documentation and commit messages are in English.**

## What is translated

The interface: buttons, links, forms, error messages, official texts (terms, privacy, about), page metadata and emails.

Not translated: user content (questions, answers, bio, name) and seed data. As on any global social network, everyone writes in whatever language they want. Internal logs (Telegram, console) are also left as they are.

## How the language is chosen

There is no language in the URL (`/login` is the same route in all of them). `i18n/request.ts` decides on every request:

1. the `NEXT_LOCALE` cookie, written by the selector (`components/locale-switcher.tsx` + `actions/locale-actions.ts`);
2. without a cookie, the first supported language in the `Accept-Language` header;
3. otherwise, English.

Routes are in English (`/my-account`, `/payments`) and the same in every language: a language prefix would collide with the public profile at `/[slug]`. The old Portuguese routes redirect (301) in `proxy.ts`.

Consequence for SEO: each URL has one version per visitor, with no `hreflang`. Accepted for now.

## Where the texts live

```text
messages/
  en.ts, pt.ts, es.ts        joins the namespaces of each language
  en/<namespace>.json         source of truth
  pt/<namespace>.json
  es/<namespace>.json
```

Namespaces: `common`, `nav`, `auth`, `account`, `profile`, `questions`, `payments`, `feed`, `legal`, `errors`, `emails`, `admin`.

`pt.ts` and `es.ts` are typed against `en.ts`, and `global.d.ts` registers the type with next-intl. So **`tsc` fails** if a key is missing in one language or if `t("...")` uses a key that does not exist.

## How to use it

```tsx
// Client Component
const t = useTranslations("payments");
const format = useFormatter();
t("minimum", { amount: format.number(cents / 100, { style: "currency", currency: "BRL" }) });

// Server Component, route handler, Server Action
const t = await getTranslations("errors");
return NextResponse.json({ error: t("unauthorized") }, { status: 401 });
```

- **Interpolation and plurals** with ICU (`{count, plural, one {# question} other {# questions}}`); markup with `t.rich`. Never concatenate translated pieces.
- **Money and dates** with `useFormatter`/`getFormatter`. The currency comes from the data (`questions.currency`: `BRL` or `USD`), never from the language.
- **Metadata** with `generateMetadata` + `getTranslations`.
- **Services (`lib/services`)** do not import next-intl: the error carries a key (`new WithdrawError("noPixKey")`) and the route or action translates it.
- **Zod schemas** with a user-facing message are factories that receive the translator.

## Adding a text

1. A new key in `messages/en/<namespace>.json`, and the same key in `pt` and `es`.
2. `t("key")` in the component.
3. `bunx tsc --noEmit`.

## Adding a language

1. The code in `locales` (`i18n/config.ts`) and the name in `common.locales` in the three languages.
2. A `messages/<code>/` folder with every namespace, and `messages/<code>.ts`.

## Tests

- `i18n/config.test.ts` covers the `Accept-Language` negotiation.
- Playwright runs with `locale: "pt-BR"` (`playwright.config.ts`): the specs check Portuguese texts.
